## 二、Standards / 可靠性

### S01 [P1] 并发区域复解析仍会覆盖候选历史

位置：`src/bio_pdf/api/routes/results.py:1048–1056`。

顺序调用现在确实写入不同文件；但编号依旧由 `len(prior) + 1` 分配，随后普通 `write_text`。两个并发请求都能读到相同事件数，写到同一个文件。

隔离复现：在两个请求读取事件列表后设置同步屏障；两次均返回 200、`attempt=1`、相同的 `candidate-1.txt`。最终文件字节只能匹配其中一个响应的 SHA，另一次响应及其历史引用已经失真。

修改要求：

- 数据库事务原子预留候选身份；候选使用唯一 ID，attempt 只是展示编号。
- 文件排他创建，完成写入后原子提交；候选记录同时保存内容和元数据哈希。
- 失败请求留下失败状态，不能复用已经分配的候选身份。

验收：两个真实并发请求返回两个独立候选；两个事件各自的文件、元数据、哈希始终对应；不能只增加顺序调用测试。

### S02 [P1] 旧执行快照仍能把刚失败的对比侧再执行一次

位置：`src/bio_pdf/application/comparison_service.py:797–800、873–887`，以类中最后的同名定义为准。

当前原子领取防止同时持有有效租约，但允许任何流程领取 `failed`。旧遍历仍能把别的重试流程刚执行失败的侧重新领取。

隔离时序：原流程阻塞于 Docling；另一个 retry 领取 MinerU 后失败；释放 Docling，原流程继续领取 MinerU。实际调用为 `['docling', 'mineru_http', 'mineru_http']`，MinerU attempt 变成 2。这不是用户再次发起的第二次重试。

修改要求：引入显式重试代次或领取快照的预期 attempt；失败侧只能由新的重试意图从 failed 原子转 queued。普通执行遍历不能无限制领取所有 failed。

验收：覆盖“另一流程已经失败”而不只是“另一流程还在 running”的并发时序；每个显式重试代次每侧最多执行一次。

### S03 [P1] 快速重启时尚未过期的孤儿比较任务仍会挂住

位置：`src/bio_pdf/api/app.py:55–61`；`comparison_service.py:241–261`。

恢复扫描只在启动时执行一次。进程崩溃后立即重启，旧侧仍有尚未过期的 900 秒租约；没有其他 queued 侧时 `recover_orphans()` 返回空。后续没有周期扫描，过期本身不会触发恢复。

修改要求：将恢复接入持续运行的调度/worker；过期后能够重新入队。可增加进程 owner/session 来识别死进程，但多实例场景不得把其他存活实例直接判死。

验收：独立进程领取后硬退出，立即重启，启动时租约尚有效；不点击 retry，租约到期后仍应自动恢复。仅设置“启动前就已过期”不足以验收。

### S04 [P2] 存活长任务没有续租，也会被当作孤儿抢占

位置：`comparison_service.py:787–802`；租约默认值见 `:162`。

只在 claim 时设置 900 秒，没有执行期间的 heartbeat。临时缩短租期至 0.02 秒，原 owner 未退出，等待过期后第二服务仍成功领取 attempt 2。真实长 PDF/云端轮询可能持续超过 15 分钟，造成重复解析或云端任务。

修改要求：按 token 条件续租，设置最大执行预算；失租后停止轮询/发布；恢复流程与续租共享同一租约规则。仅把租期改长不能替代续租。

验收：活 worker 长于初始租期但持续续租时，另一 worker 不可领取；停止心跳后才允许接管，旧 token 不可发布。

位置：`comparison_service.py`；AST 检查得到：

## 三、Spec / 需求实现

### P01 [P1] 原生短行仍会吞掉更完整的 OCR 行

对应原需求 P01。位置：`src/bio_pdf/workflow/handlers.py:881–884`。

相同位置去重使用双向子串包含。原生文本是 OCR 文本的一部分时，也直接消耗 OCR。

隔离输入：native `Ala`，框 `[10,10,40,20]`；OCR `Ala Cys`，框 `[10,10,90,20]`。输出只有 `Ala`，没有冲突，`Cys` 丢失。

修改要求：只有已保留内容完整覆盖 OCR 内容时才能消耗 OCR；反向包含需要保留更完整候选或进行可追溯拼接。几何相交只证明可能同一区域，不能证明原生已经完整。

验收：短原生/长 OCR、长原生/短 OCR、部分交叠、同文本不同位置分别测试；对残基结果校验字符和证据，不只统计行数。

### P02 [P1] 活性匹配键含解析器局部 table_id，导致跨引擎无法配对

对应原需求 P03。位置：`comparison_service.py:68–77`，尤其 `:75`；摘要生成见 `:1093–1105`。

同一活性、条件、页码和值，仅两侧 table_id 不同，结果为 `paired=0`、only_a/b 各 1。Docling 与 MinerU 的局部表格 ID 不具备跨引擎同一性，表检测数量或顺序变化就可能触发。

此外摘要没有保留完整 `Measurement.conditions`，只是取行/列首个文本，不能把这称为完整实验条件。

修改要求：

- 先按页、区域、表题/表头语义建立表格候选对应，局部 ID 仅作证据引用。
- 保留结构化实验条件；采用语义身份和候选组配对。
- 无法唯一确定时输出歧义，不按列表最后一条决定。
- 数值、单位换算和操作符比较须使用结构化值；单位大小写或数量级不能随意抹平。

验收：相同表格改 ID、表格重排、同页拆表/并表、不同实验条件、真正数值差异分别覆盖。更换局部 ID 不应让配对从成功变成全部缺失。

### P03 [P1] 坐标不越界仍被误报为坐标制式已验证

对应原需求 P04。位置：`src/bio_pdf/parsers/mineru_adapter.py:78–110、1100–1103`。

本轮增加越界检查是有效进展；但 `verified = bool(page_sizes) and not geometry_warnings` 仍将源页尺寸已知、不越界等同于坐标基准已知。

隔离 MockTransport：在 A4 fixture 中把越界框换为 `[0,0,100,100]`，不提供坐标单位或变换依据，manifest 即返回 `basis=source-pdf, verified=True`。未知的像素框或归一化框也可能碰巧落在页面范围内。

修改要求：分别记录 `page_size_verified`、`coordinate_basis_verified`、`bounds_valid`；只有有依据的单位、原点、旋转和裁剪变换才能生成可信 pt 框。未知制式保留 raw_bbox，并阻止精确证据定位承诺。

验收：覆盖 in-bounds 但基准未知、像素/pt/归一化、旋转/裁剪、非有限数和倒置框。当前无成功云样本，不能用 mock 代替真实协议坐标证明。

### P04 [P1] 来源通道没有包含表格单元格原文

对应原需求 P05。位置：`src/bio_pdf/api/routes/results.py:787–796`。

端点读取 `page.blocks`，忽略 `tables/cells`。隔离 fixture 设为 layout 页 blocks 为空、表格单元格含 `MIC 1 uM`，接口中 layout 通道完全消失。活性表格恰恰是需要人工对照的主要内容。

修改要求：每通道同时提供文本块与表格/单元格；保留行列、跨行跨列、表头、框和原始引用。无普通段落但有表格时通道仍必须存在；前端不能因为 lines 为空把有表格的通道隐藏。

验收：table-only 页、正文+表格页、空页、跨页表格；从页面可查看每个活性单元格的真实通道原文。

### P05 [P1] 区域 OCR 虽写入磁盘，却没有加入发布清单

对应原需求 P05 的可审计制品。位置：`handlers.py:1151–1154、1553–1555`。

区域 OCR 引用追加到 `extract_extra_refs`，但最终 `StageOutcome.artifact_refs` 只返回 `extract.json`，未使用这些额外引用。

真实任务 `job-a1f901cfc6ec` 与 `job-07ddb23a9182` 均有 `region-ocr.json` 文件，当前发布 manifest 的 extract 阶段却只有 `extract.json`。因此侧车没有进入已发布制品的哈希校验与完整性边界，执行记录中的“随 extract 发布 artifact ref”尚不成立。

来源端点还直接遍历 `stage_runs`（`results.py:740`），未把当前发布通道与历史/失败 attempt 明确区分。

修改要求：返回全部额外 refs；来源读取当前发布 manifest 引用并校验哈希。需要历史对照时单独列历史通道和 attempt/status，不能混成当前结果。

验收：真实执行后的 manifest 必须含区域 OCR；损坏侧车返回 `RESULT_CORRUPT`，不能静默读或忽略；增加未发布/失败 attempt 后，当前通道保持原样；旧基线切换后仍可回放原通道。

## 四、不能标记为完成的其他工作

### 1. “采用候选”实际上只是重新解析

位置：`results.py:1200–1205`。adopt 校验候选哈希后，只以原 PDF、页号和 `engine=docling` 创建任务；没有把候选内容、候选引用或哈希加入新任务输入。

因此候选 A 与候选 B 即使内容不同，采用操作也不会据此决定新任务使用哪个候选。当前测试只验证“新建了 job”，没有验证新结果来自被采用候选；前端 `IssuePanel` 也没有完整候选历史与采用入口。

执行报告已承认未自动并入，审查不把它伪装成此前承诺已经实现的功能。后续必须二选一并落实语义：

- 近期只提供重跑：端点/事件/文案明确命名“基于问题重跑”，不得记录为候选已经 adopted。
- 真正采用：新任务输入保存不可变候选 ID、内容哈希、源 SHA、原基线、区域和覆盖策略；提取阶段确实消费这些输入。人工采用的证据引用必须能追溯回候选。

这属于实现语义缺口，不是再给采用接口增加一个成功响应即可解决。

### 2. 基线身份仍存在多个口径

真实全文任务：DB/publication 与 validation 的 baseline_id 为 `e0cacf8e99bae1e5`，`ResultReader.read_published_manifest()` 补出的 baseline_id 为 `344e056fd7f8f51d`；`results.py:464–470` 的证据接口又返回 published_at。

审核当前从 review item 取 DB 基线，因此本次没有据此断言审核仍会普遍失败。但来源、候选、审核、导出和证据若要按同一基线串联，需统一对外 baseline_id，并把 manifest_sha/published_at 分别保留为独立字段。

### 3. 效果和对比验收未完成

优先为缺失的 SEQ ID 2/3/4/5、28 建立逐层诊断与人工 gold，再扩展 OCR 预算。至少记录每条序列的声明/残基区、进入 OCR 与否、OCR 原文、融合保留内容、解析拒绝原因。不能只把预算从 10 改大后宣布准确率改善。

MinerU 云端仍无成功样本，不能判断其在本项目中比 Docling 更好。获得可用配置后应在同页、同参数、同版本下完成真实对照。当前可保留 no-token 的明确失败状态，不应输出胜负结论。
