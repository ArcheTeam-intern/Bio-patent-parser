# 技术栈与工作流节点

> 一页纸概述 Bio-patent-parser 的技术选型、进程形态和处理节点。
> 最后核对：2026-10-15，对照仓库真实代码（`src/bio_pdf/`、`web/src/`、`pyproject.toml`）。

## 技术栈

### 后端核心（必装）

| 组件 | 作用 |
|---|---|
| Python 3.12 | 主语言，固定 3.12 版本 |
| pydantic 2 | 所有数据合同（文档/序列/活性/job/审核），`extra="forbid"` 严格模式 |
| pypdfium2 4 | PDF 原生文字、字符坐标、页面渲染与区域裁切（**非 OCR**） |
| typer | CLI 入口（`bio-pdf` 命令） |
| sqlite3（标准库） | 任务/阶段/审核/制品/租约的持久化（WAL + `BEGIN IMMEDIATE`） |
| uv + hatchling | 依赖管理与打包 |
| pytest | 测试运行（非 live 全量 474 passed / 4 skipped） |

### Web / API 层

| 组件 | 作用 |
|---|---|
| FastAPI + uvicorn + python-multipart | API 服务（`api` extra），同时托管前端构建产物 |
| React 18 + TypeScript + Vite | 前端工作台（`web/`），编译为 `web/dist` 静态文件 |
| TanStack Query + React Router | 数据获取/轮询与 URL 状态（页码、记录、标签页都进 URL） |
| PDF.js（pdfjs-dist） | 浏览器侧 PDF 渲染、证据高亮 |
| Vitest + Testing Library | 前端测试（24 个用例） |

### 可选 extras

| Extras | 装的依赖 | 何时用 |
|---|---|---|
| `dev` | pytest、pytest-cov、reportlab、ruff | 写测试和夹具时 |
| `api` | fastapi、uvicorn、python-multipart | 跑 API 服务 / 演示 |
| `docling` | docling SDK + httpx | **本地跑 Docling 解析**（httpx 同时覆盖远程适配器） |
| `rapidocr` | rapidocr + onnxruntime | **无系统 OCR 二进制时的 OCR 引擎**（Windows 推荐） |
| `mineru` | httpx | 调 MinerU V1 HTTP 适配器 |
| `llm` | httpx | 受约束 LLM 候选提取（第二期） |

### 外部服务（按需）

| 服务 | 用途 | 协议 |
|---|---|---|
| `docling-serve`（自托管） | Docling 远程推理 | HTTP `/v1/convert/file/async` |
| MinerU V1 SaaS | MinerU 远程推理 | `https://mineru.net/api/v4/extract/task` |
| Hugging Face（可用 `HF_ENDPOINT` 镜像） | 下载模型权重（layout-heron 等） | HTTPS |

### OCR 后端（`src/bio_pdf/parsers/ocr.py`）

- 运行时可探测两种后端：`tesseract`（系统二进制）与 `rapidocr`（纯 Python ONNX，需 rapidocr + onnxruntime 两个包都在）。
- `resolve_ocr_options()` 的行为：
  - **`auto`（默认）**：选择第一个已安装的引擎，**不会静默失败**；没有引擎才抛 `ENGINE_UNAVAILABLE`；
  - **显式请求**（`ocr_engine=tesseract|rapidocr`）：只允许该引擎，装没装如实执行/报错，**绝不切换到另一个**；
  - 语言名做别名映射（`en→iso:en`、`zh→iso:zh-Hans`、`chi_tra→iso:zh-Hant` 等），解析结果（引擎与版本）写进阶段清单。
- 未选中的引擎不参与，因此纯文字 PDF 不会触发任何 OCR。

## 运行形态（进程模型，无容器）

| 角色 | 启动方式 | 说明 |
|---|---|---|
| API 服务 | `bio-pdf serve --data-dir <dir> --web-dist web/dist --port 8420` | 只读结果 + 接收上传/建任务/审核/导出；托管前端静态文件 |
| 队列 worker | `python -m bio_pdf.workflow.queue_worker --data-dir <dir>` | 单并发领取并执行解析流水线；**必须与 API 同 data-dir** |
| Docling 子进程 | 由 worker 按任务拉起 `python -m bio_pdf.parsers.docling_child` | 隔离重型 SDK 的导入与内存，跑完即退 |

- **没有 Docker/容器**：后端是源码直接运行（venv 里 editable 安装指向 `src/`），前端是 `npm run build` 产物由 API 托管。改后端→重启对应进程；改前端→重新 build 并强刷。
- **可靠性机制**：任务租约（900s，worker 每 180s 心跳，跨阶段边界和条件提交都带围栏校验）；worker 空闲时每 5s 写 `worker_presence` 心跳，`GET /api/v1/queue/status` 报告在线 worker/排队数/数据目录；`POST /jobs/{id}/cancel` 在单事务里删租约并标记 cancelled（被取消的解析不可能再发布），`resume` 复用已完成的阶段缓存。
- **数据库**（`<data-dir>/bio.sqlite`）关键表：`jobs`、`stage_runs`、`artifacts`、`publications`、`parse_issues`、`review_items` / `review_decisions`、`record_versions` / `record_heads`、`worker_leases` / `lease_counters` / `worker_presence`、`exports`。

## 工作流节点（8 阶段状态机）

```
ingest → inspect → native_parse → layout_parse → normalize
       → extract → validate → export
```

每个节点把产物写到 `<data-dir>/jobs/<job_id>/stage_runs/<run_id>/`，阶段间通过 `ArtifactRef` 引用上游产物；缓存键包含文档哈希、页集合、输入哈希与实现版本，`resume` 只跳过验证完好的阶段。runner 最后把**不可变发布的 manifest** 写入 `jobs/<job_id>/published/`（含 `current.json` 指针镜像），下游读取（记录/导出/审核）只看发布基线。

### 1. ingest — 文件入口检查

**干什么**：检查 PDF 头、算 SHA-256、统计页数和每页几何尺寸。

**对应代码**：`src/bio_pdf/ingest/inspector.py`

**关键点**：
- 非 `%PDF-` 头 → `INPUT_NOT_PDF`；**HTML 伪装 PDF（含 BOM 头）在此被拒**并给出 content 型提示（html/empty/unknown）
- pypdfium2 打不开 → `INPUT_CORRUPT` / `INPUT_ENCRYPTED`
- 算文件 SHA-256 作为 `document_id`；同字节重传按内容寻址去重
- 无 OCR、无模型

### 2. inspect — 页面质量分析

**干什么**：每页算「文字量 / 可打印率 / 替换字符比 / 图块并集面积 / 隐藏文字标志」，把页面分到 `native / scan_suspect / text_suspect / mixed / blank / unknown`，产出**可执行的 `ParsePlan`**。

**对应代码**：`src/bio_pdf/pdf/quality.py` + `src/bio_pdf/workflow/parse_plan.py`

**关键点**：
- 图块面积用**扫描线算法**算并集，重叠图块不会算出 >100%
- 扫描页分到 `layout_ocr`，文字页分到 `layout_native`，**OCR 不在每页都跑**
- 空白页**保留**（已检查而非漏检）

### 3. native_parse — 原生文字提取

**干什么**：用 pypdfium2 读 PDF 自带的字形层，每页一个 `PdfTextPage` 拿所有矩形 → 按垂直带分组成行 → 输出 `TextBlock`（顶-左 bbox + 原文本）。

**对应代码**：`src/bio_pdf/parsers/native_adapter.py` + `src/bio_pdf/pdf/native.py`

**关键点**：
- **字形和顺序原样保留**，`text_raw` 是真实字符（不是 OCR 出来的）
- 这是**字形的真相来源**；无 OCR、无模型

### 4. layout_parse — 版面解析（重头戏）

**干什么**：执行 `ParsePlan`——连续同 `kind` 的页批量跑一次 Docling 转换：
- `layout_native` 页 → `force_backend_text = True`（**不调 OCR 模型**）
- `layout_ocr` 页 → `do_ocr = True`（用 `resolve_ocr_options` 选定的引擎）

最后把多 run 的结果**按源页号合并**；同时透传三类对象：文字 `texts`、表格 `tables`、**图区 `pictures`**。

**对应代码**：
- 调度：`src/bio_pdf/workflow/handlers.py` 的 `LayoutParseStage`（实现版本 `v7-figure-filter`）
- 子进程：`src/bio_pdf/parsers/docling_child.py`（隔离 SDK 加载）
- 三个适配器：`DoclingAdapter`（本地 SDK）/ `DoclingServeAdapter`（HTTP 自托管）/ `MinerUAdapter`（SaaS）

**关键点**：
- 模型：`docling-layout-heron` + `TableFormer` + 选定的 OCR 后端；超时 `engine_timeout_seconds` 入配置并真实生效
- 稀疏页集合（如 `{2,4}`）拆窗口跑再过滤，**不会多返回页 3**
- 缺页就 `PageCoverageMismatchError` 失败，**不假装完成**；子进程崩溃会把 stderr 尾部写进阶段错误（运行详情可展开查看）

### 5. normalize — 双通道融合 + 结构重建

**干什么**：三件事。
1. **融合**：有 layout + native 时，按空间重叠把 native 文字注入 layout 结构（有序消费、`source_aliases`），产出 job 级 `NormalizedDocument`；
2. **药敏矩阵几何重建**：对解析器漏检的无框线 R/S/I 热矩阵，用单元格几何聚类重建表结构（`source="geometry_reconstructed"`，稀疏行列裁剪并如实记录被排除数量）；
3. **图区过滤**：剔除面积过小（刊徽）、已被表格覆盖、或内容以已提取文字为主的"图片"。

**对应代码**：`src/bio_pdf/parsers/fusion.py`、`normalize_docling.py`（含 `filter_exportable_figures`）、`src/bio_pdf/parsers/grid_matrix.py`

**关键点**：
- 空白差异 → 用 native 字符，结构保留 layout；上下文长度不一致 → 留**更长的**那个
- 真正冲突 → **不静默解决**，两边全文记成 `TEXT_CONFLICT`，**禁止自动接受**
- 重建表是**候选结构**：下游必须按审核处理，绝不冒充解析器真相

### 6. extract — 领域抽取（最重）

**干什么**：多组独立规则模块从 `NormalizedDocument` 抽出生物领域对象，并登记证据。

**对应代码**：`src/bio_pdf/extract/`

**模块与分工**：

| 模块 | 抽什么 |
|---|---|
| `sequences/st25.py` | ST.25 序列表（`<210>`/`<400>` 状态机） |
| `sequences/amino_acids.py` | 三字母→一字母，未知残基保留 `unresolved` |
| `sequences/inline.py` + `references.py` + `variants.py` | 正文序列、SEQ ID 引用（锚定真实块偏移）、变体（只记关系不重建） |
| `activities/values.py` + `metrics.py` + `assays.py` | 活性值 tokenizer（含矛盾区间降级 unparsed）、指标注册表、assay 条件 |
| `activities/tables.py` + `prose.py` + `table_classifier.py` | 表格/正文活性测量、表格分类 |
| `entities.py` + `relations.py` + `evidence.py` | 实体、抗体链配对（只看 `chain_map`）、证据索引 |

**表格分派（容易记反，以此为准）**：
- `ACTIVITY_NUMERIC` → 按表头路径产数值记录；
- `SUSCEPTIBILITY` → 每个 R/S/I 单元格产一条**分类活性**（`antimicrobial_susceptibility`，entity=药名、target=菌株；轴向由词汇证据决定，药在行/列都支持），表底 CLSI 图例作为脚注随表携带；
- `INVENTORY / SCORING / UNCLASSIFIED / SEQUENCE / ASSAY_CONDITIONS` → **只保结构不产记录**，逐表记 issue 说明原因。

**关键点**：
- **不是「OCR + 一条正则」**—— 全部是手写规则
- 证据 offset 在抽取时**从真实匹配位置算**，不事后从 id 字符串反推
- 未匹配的实体→`entity_id` 留空 + 审核原因，**不近似**
- 几何重建的表挂 `TABLE_GEOMETRY_RECONSTRUCTED` issue，其记录必须过人工审核

### 7. validate — 结构化检查 + 接受决策

**干什么**：对每条记录跑检查（长度、字符表、单位、实体链接、证据存在、坐标合法），决定 `validation_state` + `acceptance_state`；规划 `ReviewItem` 队列。

**对应代码**：`src/bio_pdf/validation/` + `src/bio_pdf/review/plan.py`

**关键点**：
- **默认 `auto_accept = false`**（设计强制）：规则通过≠事实为真，没有官方参考/人工确认一律 `needs_review`
- `accepted` 只能由 `verified_reference`（匹配官方 ST.25 附件）或 `verified_human`（人工 `confirm`）触发
- 检查结果三态：`通过 / 未通过 / 未知`——**"未知"表示规则无法评估（如无参考序列可比）而非失败**
- validate 阶段只**规划**队列——真正的 `review_items` 行由 runner 在发布事务里写（防旁路写入）；发布同时登记任务配置与结果版本

### 8. export — 落地结果

**干什么**：阶段导出写 `result.json` + `sequences.csv` + `measurements.csv` 到阶段目录；API 导出（JSON / CSV / FASTA，可选 `accepted_only`）在**捕获时固定 revision 的快照**上构建（含 `baseline_id`），审核发生在排队之后也不会混入不同版本。

**对应代码**：`src/bio_pdf/export/` + `src/bio_pdf/application/result_snapshot.py`

**关键点**：
- CSV 含 `raw` / `normalized` / `operator` / `unit` / `assay` / `entity` / `target` + 校验/接受状态，**不是两列的简化版**
- `--accepted-only` 是**读时过滤**，不是破坏性操作
- 审核 `confirm/correct/reject` 写新 revision（`record_versions`/`record_heads`），old raw 永不覆盖；提交带 `base_revision`，过期返回 **409 + 双方版本号**

## 证据模型（贯穿 extract→审核→前端）

- 证据 ID 是**内容哈希**（`ev-<sha20>`，含页号），不透明、不可从字符串推断位置；同一号码不同拼写的引用（`SEQ ID No.1` vs `SEQ ID NO: 1`）各自锚定真实块偏移，不共用 ID。
- 精度分两轴：`text_precision`（offset/block/none）与 `geometry_precision`（character/cell/line/block/page/none）——**块级 bbox 绝不标成字符级**，缺坐标就如实降级。
- 证据可被前端定位：选中记录 → 证据 API 取坐标 → PDF 高亮框（可点击放大成裁切图）；绿色高亮框即块级定位。

## 审核队列（页面与语义）

- **待审核（review items）**：逐条记录的人工决定队列（序列+活性），来源是 validate 的规划 + 发布事务登记。当前演示任务单任务可达 145 条（2 序列 + 143 药敏单元格）。
- **问题（parse issues）**：解析过程的只读审计痕迹（表格分类、几何重建、图区重建剔除、零散结果提及等），解释"为什么"而不是"要你做什么"。
- 队列页：真实总数、任务筛选、分页加载；工作台头部"N 条待审核 ›"直接跳到筛选队列；队列行点击进入工作台对应记录的审核面板。

## 一次完整 run 的时间线（真实论文，12 页，docling 引擎）

| 阶段 | 耗时 | 是否调模型 |
|---|---|---|
| ingest | 0.1s | 否 |
| inspect | 0.2s | 否 |
| native_parse | 0.7s | 否 |
| layout_parse | **52s（模型已缓存）** | 是 |
| normalize | 0.2s | 否 |
| extract | 0.1s | 否 |
| validate | 0.1s | 否 |
| export | 0.1s | 否 |

说明：早期冷启动（首次下载/加载模型）实测约 245s；模型缓存后同页数约 45–90s，随机器与页数变化。**OCR 只在 inspect 标记的扫描页跑**，纯文字 PDF 全文 OCR 都不会触发。

## 数据布局（默认 `<data-dir>`）

```
<data-dir>/
├── bio.sqlite                  # 任务/阶段/审核/制品/租约
├── sources/                    # 内容寻址的源 PDF（<sha256>.pdf）
└── jobs/<job_id>/
    ├── stage_runs/<run_id>/    # 各阶段产物（+ stage 清单）
    ├── published/              # 不可变发布 manifest + current.json 指针
    └── exports/<export_id>/    # 固定 revision 的导出快照
```
